## Контекст

Гілка: !`git branch --show-current`

Статус: !`git status --short`

Staged-діф (знімок на момент виклику — після будь-якого `git add`/`git reset` він застарілий, див. крок 2): !`git diff --staged`

Unstaged-діф (лише статистика): !`git diff --stat`

Останні коміти (зразок стилю): !`git log --oneline -8`

## Завдання

Зроби **один атомарний коміт** зі змін вище. Підказка користувача про суть змін: $ARGUMENTS

### 1. Перевір, що йде в коміт

- Якщо staged порожній — додай доречні файли сам (`git add <шляхи>`), **ніколи не `git add -A` наосліп**.
- **Не комітити ніколи:** `local.properties`, `build/`, `.gradle/`, `.idea/`, `.kotlin/`, `xcuserdata`, `*.iml`, `.DS_Store`, секрети/токени/ключі. Якщо таке вже в staged — прибери через `git reset HEAD -- <шлях>` і скажи про це.
- `kotlin-js-store/*.yarn.lock` комітити **треба** — це не сміття, а залочені npm-залежності.
- Перечитай staged-діф на випадкові артефакти: закоментований код, `TODO` без контексту, налагоджувальні `println`, тимчасові файли.

### 2. Після будь-якого `git add` — перечитай staged заново

Діф у розділі «Контекст» — це **знімок на момент виклику команди**. Щойно ти виконав `git add`, `git reset HEAD -- <шлях>` або будь-що інше, що змінює індекс, цей знімок більше не описує коміт, який ти збираєшся зробити.

Тому **обов'язково**:

```bash
git diff --staged
git status --short
```

і склади повідомлення **за фактично застейдженим вмістом**, а не за початковим знімком. Це не формальність: інакше легко описати файли, яких у коміті немає, проґавити ті, що додалися, або не помітити, що в індекс заїхало сміття з крок 1.

Правило: **останній `git diff --staged` має бути виконаний після останньої зміни індексу і до `git commit`.** Якщо між ними був хоч один `add`/`reset` — перечитай ще раз.

### 3. Атомарність

Один коміт = одна логічна зміна. Якщо в staged змішані незалежні речі (напр. рефакторинг пакета + нова фіча, або зміна коду + правка доків, не пов'язана з ним) — **не комічу все разом**: розклади на кілька комітів через `git add <шляхи>` по черзі, або скажи користувачу, що саме варто розділити, і запитай.

Коли комітів кілька — правило з кроку 2 діє для **кожного** з них окремо: застейджив наступну порцію → перечитав `git diff --staged` → написав повідомлення саме під неї.

### 4. Повідомлення

Формат — Conventional Commits:

```
<type>(<scope>): <короткий imperative-заголовок>

<тіло: навіщо, а не що — лише якщо це не очевидно з діфу>

<трейлери>
```

- **type:** `feat:` (нова поведінка), `fix:` (виправлення бага), `chore:` (обслуговування, прибирання, залежності), `docs:` (документація), `test:` (лише тести), `refactor:` (зміна структури без зміни поведінки), `build:` (збірка/Gradle).
- **scope** — модуль, коли це прояснює: `core`, `server`, `shared`, `android`, `web`, `ios`. Без scope — теж нормально.
- **Заголовок:** англійською, imperative («add», «drop», «rename», не «added»/«adds»), з малої літери, без крапки в кінці, ≤ 72 символів.
- **Тіло** — англійською, пояснює **навіщо**: яку проблему знімає зміна, чому обрано саме такий шлях, що зламалося б без неї. Не переказуй діф. Якщо зміна тривіальна й самоочевидна — тіла не треба.
- Списком у тілі перелічуй лише те, що читач не побачить із заголовка (кілька пов'язаних правок в одному атомарному коміті).
- Згадуй тести рядком `Tests: <імена тестів>`, якщо коміт їх додає.

### 5. Трейлери співавторства — обов'язково

В кінці повідомлення, після порожнього рядка, додай трейлери атрибуції **точно в тому вигляді, який задано в поточній сесії Claude Code** (`Co-Authored-By:` і `Claude-Session:`). Візьми їх з інструкцій цієї сесії — **не копіюй session id зі старих комітів**, він у кожної сесії свій. Перевірити формат можна так: `git log -1 --format=%B`.

Комічу через heredoc, щоб зберегти багаторядковість:

```bash
git commit -m "$(cat <<'EOF'
feat(server): add GET /search backed by Open Library

Clients go through this endpoint instead of calling Open Library directly.

Co-Authored-By: ...
Claude-Session: ...
EOF
)"
```

### 6. Після коміту

Покажи `git log --oneline -1` і `git status --short`. Якщо дерево не чисте — скажи, що лишилося незакоміченим і чому.

### Чого не робити

- Не пушити (`git push`) — тільки якщо користувач прямо попросив.
- Не комітити в `main` — працюємо через гілки (див. AGENTS.md). Якщо поточна гілка `main`, спершу спитай.
- Не робити `git commit -a` і `git add -A` без розбору.
- Не використовувати `--no-verify`, не змінювати вже опубліковані коміти без прямого прохання.
